# Agent Note：`codex` 与 `claude-code` subagent 结果携带 `changedFiles` 与 `usage`

Status: implemented

[English](2026-08-17-subagent-delegation-changed-files-and-usage.md) | 中文

## Problem

一次委派出去的 `codex`/`claude-code` 运行早已具备回答两个父级模型经常需要知道的问题的数据——"子级究竟改动了什么、改在哪里"以及"这次运行花费了多少"——但两者都被直接丢弃了。`SubagentResult` 既不携带任何一个字段，父级也就无法把一次只读的调研委派与一次悄悄重写了文件的委派区分开来，更完全看不到子级自身的 token 花费。

三项实测确定了实现方式，而且每一项都推翻了仅凭协议文档或 SDK 自身类型文档所做的猜测：

**被拒绝的 Claude 工具调用仍会产生 `tool_use` 块。** 在 `permissionMode: 'read-only'` 下驱动一次真实的 Claude Agent SDK 0.3.220 运行并要求其创建文件，被拒绝的 `Write` 会产生一个普通的 assistant `tool_use` 块（对于 `Bash` 绕过尝试同样如此）——在 wire 上与一次成功调用毫无区别。仅凭 `tool_use` 块的存在来收集，会把一次只读运行报告为写入了文件：这不是外观上的小 bug，而是安全性的误报。

**Claude 的 `tool_use.input.file_path` 可能是相对路径。** 用 `input: { file_path: 'made.txt', content: 'WROTE\n' }` 脚本化一个 `Write` tool_use，在 `workspace-write` 下会让真实 CLI 在其自身 cwd 内创建 `made.txt`，而观察到的 assistant 消息中仍然是原始的相对字符串——SDK 自身的 `sdk-tools.d.ts` 把该字段文档化为"要修改文件的绝对路径"，但经由 wire 传来的值是模型自己给出的、未经解析的原始输出，CLI 并不会在其到达这条消息流之前先做归一化。

**Codex 的 `thread/tokenUsage/updated` 每个轮次会多次触发，且携带累积总量。** 通过一个双响应轮次（一次工具调用，随后是最终答案）驱动真实的 `codex app-server 0.147.0`，会为**同一个**轮次产生两条 `thread/tokenUsage/updated` 通知：先是 `{ total: { totalTokens: 15, inputTokens: 10, outputTokens: 5 } }`，随后是 `{ total: { totalTokens: 26, inputTokens: 20, outputTokens: 6 } }`。第二个 `total` 是整个轮次的运行总量（输入 10+10、输出 5+1——即两次底层 Responses 调用各自声明用量之和），不是增量；把两条通知的 `total` 相加（41）会让真实总量（26）翻倍。`turn/completed` 完全不携带用量信息，因此只读取终态通知的分类器什么也看不到。

第四项非计划内的实测，纠正了规格文档自身关于 Codex Bash 不对称性的假设（见"Alternatives considered"）：普通 shell 写入在**两个**提供方上都对 `changedFiles` 不可见，而不只是 Claude 一方。

## Decision

`packages/subagent/subagent/src/types.ts` 新增 `SubagentUsage`（`{ inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }`，均为 `number`）以及两个新的可选 `SubagentResult` 字段，沿用[墙钟超时](2026-08-17-subagent-delegation-timeout.md)与[失败分类](2026-08-17-subagent-delegation-failure-classification.md) Agent Note 已经为 `failure`／`authMode` 确立的"可选附加事实"模式：`changedFiles?: readonly string[]`（绝对路径，已去重）与 `usage?: SubagentUsage`。两者都没有获得 `SubagentCapabilities` 标志：二者都是**结果的输出**，不是需要提供方声明支持的请求输入（这与 `permissionMode` 不同——`permissionMode` 会拓宽子级**可以做什么**，因此按[权限范围 Agent Note](2026-08-17-subagent-delegation-permission-scope.md)的要求需要能力门禁）。`spawn`／`fork` 根本不会被问及是否填充这两个字段，也确实从不填充——挂载时没有什么可拒绝的，因此能力标志只会永远读作 `false`。`SubagentStopReasonMap` 未改动。

**`inputTokens` 的含义被固定为"含缓存"**，因为两个提供方的原生字段在这一点上恰好相反，而一个共同字段不能悄悄承载两种含义：Codex 自身的 `tokenUsage.total.inputTokens` 本就包含其 `cachedInputTokens` 子集（实测的恒等式 `totalTokens = inputTokens + outputTokens` 证明了这一点——缓存是内嵌的，不是额外叠加的），而 Claude 自身的 `usage.input_tokens` **不含** `cache_creation_input_tokens` 与 `cache_read_input_tokens`（按 Anthropic 的 `BetaUsage`，它们是各自独立、额外叠加的计数）。Codex 无需任何调整；把 Claude 的三个原生字段相加（`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`）即可得到这一共同含义。`cacheReadTokens`／`cacheWriteTokens` 直接报告每个提供方各自的原生缓存拆分（Codex：`cachedInputTokens`／`cacheWriteInputTokens`；Claude：`cache_read_input_tokens`／`cache_creation_input_tokens`）——在这一定义下，两者对两个提供方而言都是 `inputTokens` 的子集。任何一方的费用字段都不进入这份共同约定：Codex 根本没有，Claude 有 `total_cost_usd`，而把某一方的费用概念硬塞进一个"共同"字段、让另一方无法诚实地填充它，会违背此前让 `SubagentFailureCode` 保持封闭、让 `authMode` 保持普通枚举的同一条规则。

**Codex**（`subagent-codex/src/wire.ts`）：`handleNotification` 新增一个针对 `item.type === 'fileChange'` 的 `item/completed` 分支，收集进一个 `Set<string>`（去重，保留首次观察到的顺序），且**仅当** `item.status === 'completed'` 时才收集——`declined`／`failed`／`inProgress` 状态的项会被静默跳过，绝不加入。新增的 `thread/tokenUsage/updated` 分支（仅按 `threadId` 限定范围，与 `turn/started` 自身的限定范围一致）在每次到达时**覆盖** `retainedUsage`——绝不合并或相加——因此只有最后一次观察到的累积 `total` 会留存下来。`runTurn()` 的两处直接构造结果的位置（`completed` 的返回值以及 `contextWindowExceeded` → `max-tokens` 的提前返回）都会展开一个 `resultExtras()` 辅助函数，只有在非空／已定义时才附加 `changedFiles`／`usage`。`object()`／`string()`／新增的 `number()` 校验器会把格式错误的 `fileChange.changes` 或 `tokenUsage.total` 字段分类为 `protocol`，与本模块既有的形状校验严格度一致。`turn/diff/updated`（在真实 app-server 上同样观察到）被刻意弃用：它为整个轮次携带一段未经结构化的统一 diff 文本，而 `fileChange` 这种按条目、按路径、附带状态限定的结构，正是 `changedFiles` 所需要的。

**Claude**（`subagent-claude-code/src/run.ts`）：`consumeClaudeQuery` 新增一个 `cwd` 参数（在 `startClaudeCodeRun` 唯一的调用点由 `spec.cwd` 传入），并在迭代过程中，从 assistant 消息的 `tool_use` 块构建一张 `Map<toolUseId, path>` 的写入类工具候选表（`Write`／`Edit` → `file_path`，`NotebookEdit` → `notebook_path`——已对照锁定 SDK 的 `sdk-tools.d.ts` 核实；0.3.220 中没有 `MultiEdit` 工具，因此该收集器集合恰好就是权限范围 Agent Note 自身 `WORKSPACE_WRITE_ALLOWED_TOOLS` 写入子集去掉 `Bash`），以及一张记录 id 的 `Set<toolUseId>`——这些 id 在后续某条 user 消息中都有一条同 id、未报错的 `tool_result`。在终态的成功 `result` 消息处，只有当某候选项的 id 同时出现在成功集合中**且**不出现在该消息自身的 `permission_denials` 中时才会上报——是正面的成功证据，而不是"未被拒绝"，弥合了实测陷阱打开的这个安全缺口。每个被上报的路径都用 `path.resolve(cwd, candidate)` 解析——对已经是绝对路径的值这是一次空操作，对相对路径则会将其归一化——因此两个提供方上报的都是同一种绝对路径形态。`usage`／`permission_denials` 是从终态结果消息的原始记录中读取的（`claudeUsage()`／`deniedToolUseIds()`），而不是通过 SDK 自身有类型（必填、非可选）的字段——这与失败分类 Agent Note 中已经为 `is_error`／`terminal_reason` 确立的同一种防御性读取姿态一致，这里把它扩展到同一条已被证明不可完全信任的消息的另外两个字段：一个补充性的元数据字段绝不应该把一次本该成功的运行变成崩溃，这种姿态还带来一个附带效果：每一条既有的、手工构造的测试消息 fixture（从未填充过 `usage`／`permission_denials`）都能不加修改地继续通过——本改动没有产生任何 fixture 连锁反应。assistant／user 消息的 content 数组同样通过一个小的 `messageContent()` 辅助函数读取，而不是 SDK 有类型的 `message.message.content`，原因相同：某个既有测试 fixture 把一个不完整对象 `as unknown as SDKMessage` 强制转换，而元数据收集器必须能在不让已经处理该形态的分类逻辑崩溃的前提下容忍这种形态。

**`dsh-tool-subagent`**：`ForegroundToolResult` 新增可选的 `changedFiles`／`usage`，只有当 `result.changedFiles`／`result.usage` 存在时（数组还需非空）才会在 `settleForegroundRun()` 中填充。该工具的 `output.schema` 中 `'foreground'` 分支把两者都新增为可选属性（绝不要求必填）；`render()` 只有在各自存在时才会附加一段"Files changed:"清单和一行"Tokens used: … in, … out"——用缺省而不是空值来让常见的只读运行场景保持无噪音，这与该 seam 类型文档中一贯的"缺省，而绝不是空值"规则一致。

## Alternatives considered

- **让 `changedFiles` 的每一项都带一个新增／更新／删除的种类联合类型**——已否决：Claude 无法诚实地区分"创建"与"覆盖"（一次 `Write` tool_use 无论如何都是"创建或覆盖"），因此种类字段要么是只有 Codex 才有真实数据、Claude 端却要伪造出一个值，要么就是一个只在某一方存在的不对称字段。共享约定只携带路径；Codex 自身更丰富的 `fileChange.changes[].kind` 仍留在提供方内部。
- **把 `inputTokens` 定义为"不含缓存"**（保持 Claude 原生含义不变；Codex 则需要减去 `cachedInputTokens` 和 `cacheWriteInputTokens`）——经权衡后否决，选择了含缓存的定义："模型这一轮实际处理过的 token 总数"对于要判断一次运行是否昂贵的委派模型来说是更有用的共同含义，而且在 Codex 一侧完全不需要调整（它自身的 `inputTokens` 已经就是这个数），只需要在 Claude 一侧做一次求和。两种选择本身都自洽；这是一次真实的设计分岔，而不是别无选择，因此记录在这里，以免未来的读者需要从零重新推导。
- **信任 `SDKResultMessage.usage`／`permission_denials` 是 SDK 自身有类型、必填、非可选的字段**（直接读取 `message.usage`／`message.permission_denials`，不做防御性兜底）——先尝试过，随后被否决：`subagent-claude-code.spec.ts` 中每一条既有的手工构造测试消息（`success()`／`failure()`，以及用于 assistant 错误保留测试的两条字面量 `{ type: 'assistant', error: '…' } as unknown as SDKMessage` fixture）都完全没有这两个字段，因此严格读取会让大约十几个原本通过的测试崩溃，要么需要对整套 fixture 做连锁改动（给每个 mock 都加上一个伪造的 `usage`／`permission_denials`，包括那些与本特性完全无关的测试），要么就采用本 Note 实际交付的这种防御性读取风格。这种风格也具备正确的普适性：它与 `resultFields()` 已经为 `is_error`／`terminal_reason` 采用的姿态完全一致，原因同样是实测产品的 `subtype` 字段不可靠——`usage`／`permission_denials` 只是这同一条早已不受信任的消息上的另外两个字段，而不是一个新的特例。
- **假定 Codex 的操作系统沙箱会把每一次 shell 写入都捕获为一个 `fileChange` 项**（规格文档自身对 Bash 不对称性所做的假设）——已实测并证伪：在 `sandbox: 'workspace-write'` 下，通过 `exec_command`／`shell_command` 驱动真实 app-server 执行 `printf WROTE > marker.txt`，确实会创建文件，但只会上报一个 `commandExecution` 项，绝不会上报 `fileChange`。要复现实测到的那个真正的 `fileChange` 项，需要让模型调用 Codex 自身专属的 `apply_patch` 工具（一个 `custom_tool_call` 类型的 Responses 输出项——`{ type: 'custom_tool_call', name: 'apply_patch', input: <原始 patch 文本> }`，而不是携带 JSON 参数的 `function_call`——还需要 `config.toml` 中配置一个 codex 能识别的模型名；默认的 fixture 模型会退化为"unsupported call: apply_patch"）。经过修正后的事实，现已写入两个提供方各自的 README：普通 shell 写入在**任一**提供方上都对 `changedFiles` 不可见，不只是 Claude 一方；Codex 自身要求模型"始终使用 `apply_patch` 进行手动代码编辑"的系统指令，在实践中收窄了这一缺口，但并未彻底消除它。
- **只用 wire 层的回归测试覆盖累积用量陷阱**（不做真实产品层面的覆盖）——鉴于该陷阱的严重性，已否决为覆盖不足；但**只**做真实产品测试同样被否决为不充分：要通过真实 app-server 逼出一个 `declined`／`failed`／`inProgress` 的 `fileChange` 状态目前没有已知的复现方式（一次只读的 `apply_patch` 尝试会在 codex-core 为其发出任何条目之前就被操作系统沙箱拒绝——已直接实测确认），因此这一特定的状态过滤边界只能在 wire 层覆盖，这与失败分类 Agent Note 中已经采用、针对实测 401 保留逻辑的那种做法（wire 层协议测试加真实产品层面的标题测试覆盖可达路径）相互呼应。
- **把 `settleRunResult()` 中通用的 `aborted`／`error` 分支也扩展为携带部分 `changedFiles`／`usage`**（与 `authMode` 完全对称——`authMode` 确实在每个结算分支上都会附加）——推迟而非直接否决：这需要给 `RunResultSettlement` 增加与既有 `collectOutput` 平行的 `collectChangedFiles`／`collectUsage` getter，而且 Claude 的 `consumeClaudeQuery` 需要把其累积状态从函数内部提升到一个在 attempt 结算之前调用方就可见的可变对象上（Codex 的 wire 已经把这类状态作为实例字段持有，所以真正的新增工作量只在 Claude 一侧）。要求的七项测试都不需要这个特性，而 `out-of-process.ts` 保持不变也让本次改动的影响范围只限于两个提供方和这一个工具。已作为已知限制记录在共享包的 README 中，而不是在此解决。

## Consequences

- `spawn`／`fork`／`acp`／`dsh-sdk` 组合完全不受影响：`changedFiles`／`usage` 都是任何进程内提供方都不会填充的可选字段，没有能力检查需要失败，其他每个包测试中既有的 `SubagentResult` 字面量都不需要任何修改就依然合法。
- 一次 `codex`／`claude-code` 委派的 `completed`（以及 Codex 的 `max-tokens`）结果现在能告诉父级模型子级究竟改动了哪些文件（绝对路径，两个提供方均如此）以及这次运行花费了多少 token（`inputTokens`／`outputTokens`／`cacheReadTokens`／`cacheWriteTokens`，两个提供方均如此，含义统一归一化）——由 `dsh-tool-subagent` 渲染为两段可选文本，不会给常见的只读运行场景带来任何噪音。
- 无论子级什么都没尝试，还是尝试过但被拒绝，一次只读的 `codex`／`claude-code` 运行都会报告 `changedFiles: undefined`（绝不是 `[]`）——各种拒绝路径（Claude 的"`tool_use` 但无成功证据"；Codex 的"在产生任何条目之前就被拒绝"的 `apply_patch`，以及它被操作系统沙箱拦下的 shell 写入）最终都收敛到同一种安全的、以缺省表达的空结果。
- 按实测的构造方式，`changedFiles` 在两个提供方上，对于一次由 `Bash`／shell 驱动的变更都是**不完整**的：PR1 的 `workspace-write` 范围允许 Claude 使用 `Bash`，而 Codex 的操作系统沙箱允许一次不会产生 `fileChange` 项的 shell 写入。部署方不能把任何一方的 `changedFiles` 当作 `workspace-write` 下详尽无遗的审计记录——这一点已记录在两个提供方各自的 README 以及共享包自身的已知限制中。
- 在两个提供方上，`changedFiles`／`usage` 在一次 `aborted` 或未分类的 `error` 结果上都是缺省的（而不是部分填充）；只有 `completed`／`max-tokens` 结果才携带这两个字段中的任意一个。`authMode` 没有这一缺口，因为 `settleRunResult()` 会在每个结算分支上附加它，与本次改动无关。
- 真实产品测试（`subagent-codex/tests/real-product.spec.ts`、`subagent-claude-code/tests/real-product.spec.ts`）针对本地 fixture 后端，通过各自提供方自身的真实二进制文件／SDK 证明了可达路径，且不需要任何在线产品订阅：Codex 由 `apply_patch` 驱动的 `fileChange` 在 `workspace-write` 下会上报一个绝对路径，在 `read-only` 下则缺省；Claude 相对的 `Write` `file_path` 会解析为子级 cwd 下的绝对路径；一对被拒绝的 `Write`／`Bash` 不会上报任何 `changedFiles`；每个已完成的真实产品测试现在还会断言 fixture 自身确定性的 `usage` 值（两套 fixture 都声明了固定的单次响应 token 数，真实产品要么按轮次求和（Codex），要么原样转发（Claude），因此预期值是精确的，而不是近似的）。`subagent-codex.spec.ts` 新增了针对 `declined`／`failed`／`inProgress` 状态过滤、路径去重、格式错误的 `changes` 数组之 `protocol` 分类，以及双通知累积总量回归（取最后一个值而不是求和）的 wire 层协议测试。`subagent-claude-code.spec.ts` 新增了直接针对 `consumeClaudeQuery` 的拒绝排除、完全没有 `tool_result`，以及相对路径解析这几条路径的单元测试。`tool-subagent.spec.ts` 通过真实插件主体，同时证明了字段已填充时的渲染与空场景下无噪音的渲染。
