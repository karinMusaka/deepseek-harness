# Agent Note: Per-model show/hide for the composer model picker

Status: implemented

English | [中文](2026-09-24-model-picker-visibility.zh.md)

## Problem

The composer model picker and the `/model` popup list every model every configured provider advertises, with no way for a user to trim that list down to the models they actually use. A user with several provider catalogs configured (a pi-ai route serving dozens of models, DeepSeek's own catalog) gets a long, undifferentiated menu on every open. There was no durable per-model preference anywhere in the settings surface, and the two selection entries (`ModelSelect` and the `/model` popupSelect) already share one `ModelDirectory` per session, so any fix had to land once, in that shared point, rather than twice in each entry's own rendering.

## Decision

`ModelDirectory` (`packages/client/ui-model-selection/src/client/directory.ts`) is the sole enforcement point: it filters the advisory `groups` both selection entries render against a durable `hiddenModels` preference, and nothing else — `session.models` and `session.selectModel` stay exactly as advertised by the Host. Filtering is client-side, not server-side (`buildModelCatalog` in `packages/host/apiproxy/src/api-proxy.ts` is untouched), because the Host catalog is explicitly advisory — README language already establishes that catalog membership never gates routability — and keeping the routing-affecting catalog and the display-affecting preference in two different layers means a hidden model that is still someone's current selection keeps routing through the unfiltered Host response with no special-casing on the wire.

The durable namespace (`ui-model-selection`, field `hiddenModels: Record<provider, string[]>`) is registered by `ui-model-selection`'s own node half (`packages/client/ui-model-selection/src/index.ts`), following the `ui-theme` pattern exactly: `ctx.inject(['settings'], …)` around `settings.register`, schema and constants in a small module (`src/model-visibility-settings.ts`) shared between both plugin halves. The package that renders the picker owns the namespace that controls it, matching `ui-theme` owning `ui-theme.preference` for its own Appearance row — a feature owns its own settings surface. `ModelDirectoryResolver` (the per-connection service backing every session's `ModelDirectory`) binds ONE shared `ctx.settingsScope` scope for this namespace, since the preference is a user setting, not a per-session fact, and passes it into each `ModelDirectory` it constructs. Each directory keeps its last good *raw* (unfiltered) `groups` privately and re-derives the *shown* `groups` both after a fresh load/selection and on every change to the shared scope's snapshot — a network-free refilter, decoupled from `ModelDirectoryResolver`'s separate `settings/document-updated` → full reload path, which exists for unrelated catalog/topology changes and races independently against the scope's own refresh.

The current selection is exempt from hiding: `filterGroups` (`packages/client/ui-model-selection/src/client/visibility.ts`) never removes the exact current provider/model pair, only re-deriving a different one on the next `select()`. Without this exemption a user could hide their own current model and the trigger would silently fall back to "Select model" — indistinguishable from a real catalog failure — which the picker's own contract already forbids for the unrelated "unadvertised but current" case.

Fail-open governs every unready state: `ModelDirectory` reads the scope's `getSnapshot().status`, and anything other than `'ready'` (loading, `'unavailable'`, or a remote browser's process-local `'memory'` mode) is treated as an empty hidden set. The picker must never go empty because this preference's own transport is slow, absent, or unsupported in this session's connection mode.

`@deepseek-ai/dsh-client-ui-settings-models`'s Models page is the only writer: a new "Models shown in the picker" section lists every provider group from the *unfiltered* Host catalog (`llm.models`, independent of any session's advisory directory) with one checkbox per model plus a per-provider show-all/hide-all control, writing `settings.mutate` path ops directly at `ui-model-selection.hiddenModels.<provider>` (`unset` once a provider's list empties, `set` with the complete array otherwise) and reloading the whole page snapshot on both success and `settings-conflict`. It cannot import `ui-model-selection`'s namespace/field constants — `packages/client/AGENTS.md`'s cross-package-import ban applies to plugin packages generally, and `dsh-client-ui-settings-models`'s own `apiKey.ts` already documents the same resolution for `normalizeApiKey`'s twin — so the namespace id and field name are mirrored string literals with a comment explaining why, the same pattern the page already uses for `llm-deepseek`/`llm-pi-ai`, namespaces it does not own either.

The task's literal "ja/zh/en" locale requirement was narrowed to zh/en: no client package in this repository defines a `ja` locale, `LocaleNamespaceMap` has no Japanese variant, and the product-copy rule is "Chinese product copy; English comments" — adding a third locale mechanism has no other consumer and is out of scope for this change.

## Alternatives considered

**Filter in `buildModelCatalog` (Host-side).** Rejected: `session.models`/`llm.models` are the advisory catalog contract multiple surfaces read (the picker, and now the visibility section's own unfiltered listing); folding a display preference into it would make the settings page's "show every model to un-hide" listing filter itself out, and would require a session-scoped read of a user-scoped preference at every catalog build.

**One `settingsScope` binding per session (inside `ModelDirectory` itself).** Rejected: the preference is a user setting, not a session fact, so one shared binding on the long-lived `ModelDirectoryResolver` is the correct lifecycle — it avoids N redundant `settings.describe` round trips (one per open session) and N redundant push-event listeners for what is one durable value.

**A shared exported `filterGroups`/`isModelHidden` module both packages import.** Rejected after checking the client bundle purity gate (`packages/client/tsdown.client.ts`) and `packages/client/AGENTS.md`'s export-discipline rules: cross-package value imports between plugin packages are forbidden outside slots/services, and `ui-settings-models` never needs the filtering logic itself (only a one-line hidden-set membership check on its own `hiddenModels` read) — mirroring the two small string constants is proportionate; sharing the schema-and-type module stays intra-package only, exactly like `ui-theme/src/theme-settings.ts`.

## Consequences

Hiding a model is a pure display preference: it never touches `session.selectModel`, the assembled request, or an already-current model's routability, and it is per-user-settings document-wide rather than per-session (`packages/client/ui-model-selection/README.md`'s Known Limitations now states both). Package tests cover the pure filter helpers (`tests/visibility.client.spec.ts`), the directory's live refilter-without-reload behavior and fail-open paths (`tests/browser-plugin.client.spec.ts`), host-namespace registration/disposal (`tests/host.client.spec.ts`), the settings-page store's soft catalog load (`tests/store.client.spec.ts`), and the new section's render/toggle/bulk-toggle/conflict behavior (`tests/model-visibility-section.client.spec.tsx`), plus one integration test proving the section's `reload` callback reaches the real `ModelsSettingsStore.load()`. No keyless web-browser-snapshot scenario was added: expressing a Settings-page checkbox toggle followed by an observed composer-picker change needs either a recorded fixture or new snapshot-harness multi-surface support neither of which exists today; this is a reported gap, not an implemented one.
