# Agent Note: `codex` and `claude-code` subagent results carry `changedFiles` and `usage`

Status: implemented

English | [中文](2026-08-17-subagent-delegation-changed-files-and-usage.zh.md)

## Problem

A delegated `codex`/`claude-code` run already has the data to answer two questions the parent model routinely needs — "did the child actually change anything, and where" and "how much did this cost" — but both were discarded. `SubagentResult` carried neither field, so a parent could not tell a read-only research delegation from one that silently rewrote a file, and could not see a child's own token cost at all.

Three measurements settle the implementation and each breaks a guess built from the protocol docs or the SDK's own type documentation alone:

**A denied Claude tool call still produces a `tool_use` block.** Driving a real, unauthenticated-relative-to-scope Claude Agent SDK 0.3.220 run under `permissionMode: 'read-only'` and asking it to create a file produces an ordinary assistant `tool_use` block for the denied `Write` (and, for a `Bash` bypass attempt, for that too) — indistinguishable on the wire from a successful call. Collecting `tool_use` blocks by presence alone reports a read-only run as having written files: not a cosmetic bug, a safety misreport.

**Claude's `tool_use.input.file_path` can be relative.** Scripting a `Write` tool_use with `input: { file_path: 'made.txt', content: 'WROTE\n' }` under `workspace-write` makes the real CLI create `made.txt` inside its own cwd, and the observed assistant message still carries the raw relative string — the SDK's own `sdk-tools.d.ts` documents the field as "The absolute path to the file to modify," but the value crossing the wire is the model's own unresolved output, not something the CLI normalizes before it reaches this stream.

**Codex's `thread/tokenUsage/updated` fires several times per turn carrying a cumulative total.** Driving a real `codex app-server 0.147.0` through a two-response turn (a tool call, then the final answer) produces two `thread/tokenUsage/updated` notifications for the SAME turn: `{ total: { totalTokens: 15, inputTokens: 10, outputTokens: 5 } }` then `{ total: { totalTokens: 26, inputTokens: 20, outputTokens: 6 } }`. The second `total` is the running total for the whole turn (10+10 input, 5+1 output — the sum of both underlying Responses calls' own declared usage), not a delta; summing the two notifications' totals (41) would double the real total (26). `turn/completed` carries no usage at all, so a classifier that only reads the terminal notification sees nothing.

A fourth, unplanned measurement corrected the spec's own assumption about Codex's Bash asymmetry (see Alternatives considered): a plain shell write is invisible to `changedFiles` on BOTH providers, not just Claude's.

## Decision

`packages/subagent/subagent/src/types.ts` adds `SubagentUsage` (`{ inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }`, all `number`) and two new optional `SubagentResult` fields, following the same "optional additional fact" pattern the [timeout](2026-08-17-subagent-delegation-timeout.md) and [failure-classification](2026-08-17-subagent-delegation-failure-classification.md) Notes already established for `failure`/`authMode`: `changedFiles?: readonly string[]` (absolute, deduplicated) and `usage?: SubagentUsage`. Neither gets a `SubagentCapabilities` flag: both are RESULT OUTPUTS, not request inputs a provider must be asked to support (unlike `permissionMode`, which widens what a child may DO and therefore needed a capability gate per the [permission-scope Note](2026-08-17-subagent-delegation-permission-scope.md)). `spawn`/`fork` are simply never asked to populate either field and never do — there is nothing to reject at mount time, so a capability flag would exist only to always read `false`. `SubagentStopReasonMap` is unchanged.

**`inputTokens`'s meaning is fixed as cache-INCLUSIVE**, because the two providers' native fields disagree on this exact point and a common field cannot silently mean two things: Codex's own `tokenUsage.total.inputTokens` already includes its `cachedInputTokens` subset (the measured identity `totalTokens = inputTokens + outputTokens` proves this — cache is embedded, not additive), while Claude's own `usage.input_tokens` EXCLUDES both `cache_creation_input_tokens` and `cache_read_input_tokens` (they are separate, additive counts per Anthropic's `BetaUsage`). Codex needs no adjustment; Claude's three native fields are summed (`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`) to reach the common meaning. `cacheReadTokens`/`cacheWriteTokens` report each provider's own native cache breakdown directly (Codex: `cachedInputTokens`/`cacheWriteInputTokens`; Claude: `cache_read_input_tokens`/`cache_creation_input_tokens`) — both are subsets of `inputTokens` for both providers under this definition. Neither provider's money field enters the contract: Codex has none, Claude has `total_cost_usd`, and pushing one provider's cost concept into a "common" field the other cannot populate honestly would violate the same rule that kept `SubagentFailureCode` closed and `authMode` a plain enum.

**Codex** (`subagent-codex/src/wire.ts`): `handleNotification` gains an `item/completed` branch for `item.type === 'fileChange'`, collected into a `Set<string>` (dedup, first-observed order) ONLY when `item.status === 'completed'` — a `declined`/`failed`/`inProgress` item is silently skipped, never added. A new `thread/tokenUsage/updated` branch (scoped by `threadId` only, matching `turn/started`'s own scoping breadth) OVERWRITES `retainedUsage` on every arrival — never merges or sums — so only the last observed cumulative `total` survives. `runTurn()`'s two direct result-construction sites (the `completed` return and the `contextWindowExceeded` → `max-tokens` early return) both spread a `resultExtras()` helper that adds `changedFiles`/`usage` only when non-empty/defined. `object()`/`string()`/a new `number()` validator classify a malformed `fileChange.changes` or `tokenUsage.total` field as `protocol`, matching the module's existing shape-validation rigor. `turn/diff/updated` (also observed on the real app-server) is deliberately unused: it carries one unstructured unified-diff blob for the whole turn, while `fileChange`'s per-item, per-path, status-qualified shape is exactly what `changedFiles` needs.

**Claude** (`subagent-claude-code/src/run.ts`): `consumeClaudeQuery` gains a `cwd` parameter (threaded from `spec.cwd` at the one call site in `startClaudeCodeRun`) and, while iterating, builds a `Map<toolUseId, path>` of write-tool candidates from assistant messages' `tool_use` blocks (`Write`/`Edit` → `file_path`, `NotebookEdit` → `notebook_path` — verified against the pinned SDK's `sdk-tools.d.ts`; there is no `MultiEdit` tool in 0.3.220, so the collector set is exactly the permission-scope Note's own `WORKSPACE_WRITE_ALLOWED_TOOLS` write subset minus `Bash`) and a `Set<toolUseId>` of ids with a same-id, non-error `tool_result` from a later user message. At the terminal successful `result` message, a candidate is reported ONLY when its id is in the success set AND absent from that message's own `permission_denials` — positive success evidence, not absence-of-denial, closes the safety gap the measured trap opened. Every reported path is resolved with `path.resolve(cwd, candidate)`, which is a no-op for an already-absolute path and normalizes a relative one, so both providers report the same absolute shape. `usage`/`permission_denials` are read off the raw result-message record (`claudeUsage()`/`deniedToolUseIds()`), not through the SDK's own typed (required, non-optional) fields — the same defensive-read posture `resultFields()` already established for `is_error`/`terminal_reason` in the failure-classification Note, extended here for two more fields of that same measured-unreliable message: a supplementary metadata field must never flatten an otherwise-successful run to a crash, and this posture also means every existing hand-built test-fixture message (which never populated `usage`/`permission_denials`) keeps passing unmodified — no fixture ripple from this change. The assistant/user message content arrays are likewise read via a small `messageContent()` helper rather than the SDK's typed `message.message.content`, for the identical reason: an existing test fixture casts a partial object `as unknown as SDKMessage`, and a metadata collector must tolerate that shape without crashing the classification logic that already handles it.

**`dsh-tool-subagent`**: `ForegroundToolResult` gains optional `changedFiles`/`usage`, populated in `settleForegroundRun()` only when `result.changedFiles`/`result.usage` are present (and non-empty for the array). The tool's `output.schema` `'foreground'` variant adds both as optional properties (never required); `render()` appends a "Files changed:" list and a "Tokens used: … in, … out" line only when each is present — omission, not an empty value, is how the common read-only-run case stays noise-free, matching the same "absent, never empty" rule the seam type documents.

## Alternatives considered

- **A `changedFiles` entry with an add/update/delete kind union** — rejected: Claude cannot honestly distinguish "create" from "overwrite" (a `Write` tool_use is create-or-overwrite either way), so a kind field would be Codex-only real data with a fabricated Claude value, or an asymmetric field present for one provider and not the other. The shared contract carries paths only; Codex's own richer `fileChange.changes[].kind` stays provider-internal.
- **`inputTokens` defined as cache-EXCLUSIVE** (Claude's native meaning, unchanged; Codex would subtract `cachedInputTokens` and `cacheWriteInputTokens`) — considered and rejected in favor of the cache-inclusive definition: "total tokens the model actually processed this turn" is the more useful common meaning for a delegating model deciding whether a run was expensive, and it requires zero adjustment on the Codex side (its own `inputTokens` is already that number), only a sum on the Claude side. Either choice is internally consistent; this was a real design fork, not a forced move, and is recorded here so a future reader does not re-derive it from nothing.
- **Trusting `SDKResultMessage.usage`/`permission_denials` as the SDK's own required, non-optional typed fields** (a direct `message.usage`/`message.permission_denials` read, no defensive fallback) — tried first, then rejected: every existing hand-built test message in `subagent-claude-code.spec.ts` (`success()`/`failure()`, and the two literal `{ type: 'assistant', error: '…' } as unknown as SDKMessage` fixtures used for assistant-error retention tests) omits both fields entirely, so a strict read would have crashed roughly a dozen passing tests requiring either a fixture-wide ripple (adding a fabricated `usage`/`permission_denials` to every mock, including tests that have nothing to do with this feature) or the defensive-read style this Note ships instead. The defensive style also generalizes correctly: it is the same posture `resultFields()` already uses for `is_error`/`terminal_reason` because the measured product's `subtype` field is unreliable, so `usage`/`permission_denials` are two more fields of that same already-distrusted message, not a new exception.
- **Assuming Codex's OS sandbox captures every shell write as a `fileChange` item** (the spec's own stated assumption for the Bash asymmetry) — measured and falsified: driving the real app-server through `exec_command`/`shell_command` running `printf WROTE > marker.txt` under `sandbox: 'workspace-write'` creates the file but reports only a `commandExecution` item, never `fileChange`. Reproducing the actual measured `fileChange` item required the model calling Codex's own dedicated `apply_patch` tool (a `custom_tool_call` Responses output item — `{ type: 'custom_tool_call', name: 'apply_patch', input: <raw patch text> }`, not a JSON-arguments `function_call` — requiring a codex-recognized model name in `config.toml`; the default fixture model falls back to "unsupported call: apply_patch"). The corrected fact, now in both providers' READMEs: a plain shell write is invisible to `changedFiles` on EITHER provider, not just Claude's; Codex's own system instructions telling the model to "Always use `apply_patch` for manual code edits" narrow this gap in practice without closing it.
- **A wire-level-only regression test for the cumulative-usage trap** (no real-product coverage) — rejected as insufficient given the trap's severity, but a PURE real-product test was also rejected as insufficient on its own: forcing a `declined`/`failed`/`inProgress` `fileChange` status through the real app-server has no known reproduction (a read-only `apply_patch` attempt is rejected by the OS sandbox before codex-core emits any item for it at all — confirmed by direct measurement), so that specific status-filter edge is covered only at the wire level, mirroring the accepted split the failure-classification Note already used for the measured-401 retention test (wire-level protocol test plus a real-product headline test for the reachable paths).
- **Extending `settleRunResult()`'s generic `aborted`/`error` branches to also carry partial `changedFiles`/`usage`** (full symmetry with `authMode`, which IS attached on every settlement branch) — deferred, not rejected outright: it would need `RunResultSettlement` to grow `collectChangedFiles`/`collectUsage` getters parallel to the existing `collectOutput`, and Claude's `consumeClaudeQuery` would need its accumulating state hoisted out of the function into a mutable object visible to the caller before the attempt settles (Codex's wire already has this state as instance fields, so only the Claude side is genuinely new work). None of the seven required tests need this, and `out-of-process.ts` staying untouched keeps this PR's blast radius to the two providers and the tool. Recorded as a Known Limitation in the shared package's README rather than solved here.

## Consequences

- A `spawn`/`fork`/`acp`/`dsh-sdk` composition is completely unaffected: `changedFiles`/`usage` are optional fields no in-process provider ever populates, no capability check exists to fail, and every existing `SubagentResult` literal in every other package's tests stays valid without modification.
- A `codex`/`claude-code` delegation's `completed` (and Codex's `max-tokens`) result now tells the parent model which files actually changed (absolute paths, both providers) and how many tokens the run cost (`inputTokens`/`outputTokens`/`cacheReadTokens`/`cacheWriteTokens`, both providers, one normalized meaning) — rendered by `dsh-tool-subagent` as two optional text sections that add no noise to the common read-only-run case.
- A read-only `codex`/`claude-code` run reports `changedFiles: undefined` (never `[]`) whether the child attempted nothing or attempted and was denied — the denial paths (Claude's `tool_use`-without-success-evidence; Codex's rejected-before-any-item `apply_patch`, and its OS-sandboxed shell write) all converge on the same safe, empty-by-absence outcome.
- `changedFiles` is INCOMPLETE by measured construction, on both providers, for a `Bash`/shell-driven change: PR1's `workspace-write` scope allows `Bash` for Claude, and Codex's OS sandbox permits a shell write that produces no `fileChange` item. A deployment cannot treat either provider's `changedFiles` as an exhaustive audit trail under `workspace-write` — documented in both providers' READMEs and the shared package's own Known Limitations.
- `changedFiles`/`usage` are absent (not partially populated) on an `aborted` or unclassified `error` result on both providers; only a `completed`/`max-tokens` result carries either field. `authMode` does not share this gap because `settleRunResult()` attaches it on every settlement branch, independent of this PR.
- Real-product tests (`subagent-codex/tests/real-product.spec.ts`, `subagent-claude-code/tests/real-product.spec.ts`) prove the reachable paths through each provider's own real binary/SDK against a local fixture backend, with no live product subscription: Codex's `apply_patch`-driven `fileChange` reports an absolute path under `workspace-write` and is absent under `read-only`; Claude's relative `Write` `file_path` resolves to an absolute path under the child's cwd; a denied `Write`/`Bash` pair reports no `changedFiles`; every completed real-product test now also asserts the fixture's own deterministic `usage` value (both fixtures declare fixed per-response token counts that the real product either sums per-turn (Codex) or relays as-is (Claude), so the expected values are exact, not approximate). `subagent-codex.spec.ts` adds wire-level protocol tests for the `declined`/`failed`/`inProgress` status filter, path deduplication, a malformed `changes` array's `protocol` classification, and the two-notification cumulative-total regression (last value, not the sum). `subagent-claude-code.spec.ts` adds unit tests for the denial-exclusion, no-tool-result-at-all, and relative-path-resolution paths directly against `consumeClaudeQuery`. `tool-subagent.spec.ts` proves both the populated-fields render and the noise-free empty-case render through the real plugin body.
