# Agent Note: `codex` and `claude-code` subagent failures classify into auth/quota/provider/protocol, with `auth_mode`

Status: implemented

English | [中文](2026-08-17-subagent-delegation-failure-classification.zh.md)

## Problem

Every native `codex`/`claude-code` delegation failure — an expired login, an exhausted quota, a provider outage, a malformed app-server frame — flattened to the same fixed string, `'subagent run failed'`. The native diagnostic that would tell the delegating model what to do next (retry, stop, or tell the user to log in) reached only `ctx.logger.warn`, a sink the model never sees. `SubagentResult` had no field to carry it, so the loss was structural, not a phrasing choice.

Classifying Codex looked trivial from the protocol docs alone — read `turn.error.codexErrorInfo` off the terminal `turn/completed` notification — and that implementation would have shipped silently broken. Measured against a real unauthenticated `codex app-server 0.147.0` (empty `HOME`, driven over the real JSON-RPC transport, not simulated):

```jsonc
// Five retryable intermediate notifications carry the real cause:
{"method":"error","params":{
  "error":{"message":"Reconnecting... 2/5",
           "codexErrorInfo":{"responseStreamDisconnected":{"httpStatusCode":401}},
           "additionalDetails":"unexpected status 401 Unauthorized: Missing bearer …"},
  "willRetry":true,"threadId":"…","turnId":"…"}}

// The terminal turn/completed degrades it to the literal "other":
{"method":"turn/completed","params":{"turn":{
  "status":"failed",
  "error":{"message":"unexpected status 401 Unauthorized: Missing bearer …",
           "codexErrorInfo":"other","additionalDetails":null}}}}
```

`wire.ts`'s `handleNotification` did not handle the `error` method at all — the only place the specific cause ever appears. A classifier reading only the terminal turn would report `provider`, never `auth`, on every real unauthenticated run. Separately, Claude Code's own result message defeats the obvious `subtype === 'success'` success check: measured against a real logged-out Claude Agent SDK 0.3.220, `is_error: true` while `subtype` stays `'success'`, with the practical login instruction landing in `result`, not `errors`.

## Decision

`packages/subagent/subagent/src/types.ts` adds a closed, non-merge-extensible `SubagentFailureCode = 'auth' | 'quota' | 'provider' | 'protocol'` and `SubagentFailureDetail { code, message }`, orthogonal to `SubagentStopReasonMap` for the same reason the [timeout Note](2026-08-17-subagent-delegation-timeout.md) kept its own new fact off that map: stop reason answers "why did the run end", this answers "what kind of failure was it", and only when the answer to the first is `'error'`. `SubagentResult` gains two new optional fields: `failure?: SubagentFailureDetail` (present only when a provider could classify an `'error'` stop reason) and `authMode?: 'subscription' | 'api-key'` (present only for the two out-of-process product providers). Every consumer switch on `SubagentFailureCode` closes its default case with `assertNever` — this union is ours to close. The vendor enums it classifies FROM (`codexErrorInfo`, `SDKAssistantMessageError`) are external and open: their own default cases fall through to `'provider'`, never `assertNever`, so a future app-server or SDK release degrades gracefully instead of crashing the harness.

**Alignment with the existing taxonomy** ([2026-06-11 Note](../architecture/2026-06-11-structured-error-taxonomy.md)) is mechanical, not cosmetic: `dsh-subagent` already exports `SubagentError extends HarnessError` for the seam's own infrastructure faults (`NO_PROVIDER`, `DUPLICATE_PROVIDER`, …). `dsh-tool-subagent` reuses that same class for a classified failure, with new codes `SUBAGENT_AUTH` / `SUBAGENT_QUOTA` / `SUBAGENT_PROVIDER` / `SUBAGENT_PROTOCOL` — not `dsh-llm`'s `MISSING_CREDENTIAL`/`INVALID_CREDENTIAL`/`QUOTA`, which name a different failure domain (the harness's *own* credential store or its *own* LLM adapter route, not a delegated child product's independent login state). Throwing `SubagentError` from the existing `stopReasonFailure` → `settleForegroundRun` throw site means the routable `code` reaches `ToolExecutionResult.error.info` — and, through the agent loop's existing forwarding, the `tool/result` session event — entirely through the pipe the June Note already built (`errorInfo()`'s `instanceof HarnessError` check). No new session event; no parallel classification mechanism.

**Codex** (`subagent-codex/src/wire.ts`): `handleNotification` gains an `error`-method branch (thread/turn-scoped exactly like `item/completed`, including the early-arrival queue for a notification that outruns `turn/start`'s own response). It retains the most specific `codexErrorInfo` label and any object-variant `httpStatusCode` seen across the turn: a label other than `'other'` always overwrites the retained value, but `'other'` never overwrites an already-retained specific one. `classifiedTurnFailure` builds the failure at `turn/completed` from the retained state, falling back to the terminal turn's own (possibly degraded) `codexErrorInfo` only when no `error` notification fired at all. `classifyCodexFailure` implements the measured table: `httpStatusCode === 401` or `codexErrorInfo === 'unauthorized'` → `auth`; `httpStatusCode === 429` or `'usageLimitExceeded'`/`'serverOverloaded'` → `quota`; everything else → `provider`. `object()`/`string()` — the wire's own JSON-RPC shape validators — now throw `ClassifiedSubagentFailure` with `code: 'protocol'`: this is the spec's own definition of that class, and it costs nothing extra since these two functions are the wire's only shape-validation surface.

**Claude** (`subagent-claude-code/src/run.ts`): `resultFields()` reads `is_error`/`terminal_reason`/`api_error_status`/`result`/`errors` off the raw message object instead of narrowing through the SDK's own `SDKResultMessage` union — that union's discriminant (`subtype`) is exactly what the measured logged-out run proved unreliable. `consumeClaudeQuery` also now consumes `assistant` messages (previously skipped entirely) to retain the most specific classifiable `SDKAssistantMessageError` (`authentication_failed`/`oauth_org_not_allowed` → `auth`; `rate_limit`/`billing_error`/`overloaded` → `quota`; the rest → `provider`; `max_output_tokens` is a per-message truncation note, not a terminal-failure signal, and is skipped). At the terminal `result` message, `is_error` (never `subtype`) decides failure at all; the retained assistant cause wins over `api_error_status` (401/429), which wins over the generic `provider` default. `'protocol'` never arises for Claude: the SDK abstracts its own wire transport entirely (Known Limitations in the package README).

`ClassifiedSubagentFailure extends Error` (`dsh-subagent/src/out-of-process.ts`) is the package-private carrier: a provider's turn attempt throws it, and `settleRunResult`'s catch extracts `.failure` onto the settled `SubagentResult` when the caught value is one, exactly like the existing `onError` diagnostic-sink extraction it sits beside. `RunResultSettlement` also gains an optional `authMode`, merged onto every settled branch (success, aborted, error alike) — it is a fact about the child's identity, not its outcome, so it is not a return-style special case.

`authMode` (Phase 2-5) is derived purely from configuration, per the brief's explicit prohibition on probing `~/.claude`/`~/.codex`: each provider's `index.ts` computes `SENSITIVE_ENV_PATTERN.test(key)` (the same regex `@deepseek-ai/dsh-subprocess`'s `scrubbedParentEnv` already uses to keep a credential out of the child's inherited environment) over `Config.env`'s own keys — `scrubbedParentEnv` guarantees that regex is the *only* path an API key reaches the child, so testing it against the deployment's own explicit `env` is a complete check, not a heuristic.

**Redaction** (`dsh-tool-subagent`): this PR is the first to route native provider text into a model-visible result and, through it, the session log. `redactCredentialShapedText` matches a credential-shaped label (the same `SENSITIVE_ENV_PATTERN` vocabulary, reused via its `.source` rather than duplicated) immediately followed by `:`/`=` and a value, and redacts only the value. It runs once, centrally, in `classifiedFailureHeadline` — not scattered across every site that could construct a `SubagentFailureDetail.message` — so the screening step has exactly one reviewable location.

## Alternatives considered

- **Classifying Codex from the terminal `turn.error.codexErrorInfo` alone** — rejected on direct measurement (see Problem): a real unauthenticated run degrades that field to the literal `"other"`, so this implementation would classify every real 401 as `provider` and never `auth`. This is the most important rejected alternative in this Note: it is the one a reader would write first from the protocol docs alone, and it silently never matches.
- **Consuming Claude's assistant messages for `SDKAssistantMessageError`** vs. classifying from the result message's `api_error_status` alone — the spec left this to the implementer with a recording duty either way. Chosen: consume them. The result message's `api_error_status` is `null` in the measured logged-out capture (a local CLI rejection makes no HTTP call at all), so a result-only classifier would need a text-pattern heuristic on `result` to reach `auth` for that exact case — fragile against a wording change. The assistant message's own `error: "authentication_failed"` is a clean, versioned enum from the pinned SDK's own types for the identical scenario, so it is retained as the primary signal, with `api_error_status` (401/429) as the fallback for any future case where an assistant-message cause is absent.
- **Reusing `dsh-llm`'s `MISSING_CREDENTIAL`/`INVALID_CREDENTIAL`/`QUOTA` codes** for the classified `SubagentError` — rejected: those name failures in the harness's *own* credential store or its *own* LLM adapter's request path. A delegated Codex/Claude Code child's login state is a different, product-owned identity; reusing the same code string across both would make a future retry/sandbox plugin's `switch (error.code)` conflate two unrelated recovery actions ("refresh the harness's stored key" vs. "the delegated child's own login expired").
- **A new `SubagentFailureError` class parallel to `SubagentError`** — considered and rejected: `dsh-subagent` already exports `SubagentError extends HarnessError` for exactly this seam's typed failures. A second class for a second kind of subagent-seam failure duplicates the class the June taxonomy Note asked every seam to converge on; a new `code` on the existing class is the smaller, correctly-scoped change.
- **A keyless snapshot that spawns the real `codex`/`claude-code` binary** — rejected: the existing `product-subagent-codex.cordis.yml` deliberately "pins the assembled request schema without starting Codex" (its own comment), and the package-level `real-product.spec.ts` suites already prove the real-binary path (see Tests). The shipped snapshot instead follows the established `subagent-durability-failure.ts` pattern: a snapshot-only fixture plugin wraps `ctx.subagents.start()` to replace a real forked child's settled result with a fixed classified failure after that child's real (scripted, keyless) turn completes — proving `dsh-tool-subagent`'s new text-construction code exactly, without a second, slower, less portable way to fail a child.

## Consequences

- A `spawn`/`fork`/`acp`/`dsh-sdk` composition that never encounters a `codex`/`claude-code` provider is unaffected: `failure` and `authMode` are optional fields those providers never populate, and no existing `SubagentResult` literal needed the field to stay valid.
- A `codex` or `claude-code` delegation failure now reaches the model with a class-specific headline (`"subagent could not authenticate with its provider: …"`, `"…hit its provider's usage limit: …"`, `"…provider failed: …"`, `"…provider violated its own protocol: …"`) plus the provider's own actionable text, screened for credential-shaped patterns, and a routable `SUBAGENT_*` code on `ToolExecutionResult.error.info` for a future retry/sandbox plugin.
- `SubagentStopReasonMap` is untouched; a non-`'error'` stop reason (`aborted`, `max-tokens`, `refusal`, an unrecognized future reason) never carries a `failure` and reports exactly as it did before this PR.
- Real-product tests (`subagent-codex/tests/real-product.spec.ts`, `subagent-claude-code/tests/real-product.spec.ts`) prove both directions through each provider's own real binary/SDK against a local fixture backend, with no live product subscription: a fixture-served 401 classifies as `auth` through the full retention path (Codex), and a genuinely omitted `ANTHROPIC_API_KEY` classifies as `auth` with the exact `"Not logged in · Please run /login"` text (Claude) — the fixture backend is never even called for the Claude case, since the real CLI rejects it locally. `usageLimitExceeded`/`serverOverloaded`/`httpStatusCode: 429` (Codex) and `rate_limit`/`billing_error`/`overloaded` (Claude) are covered by literal enum values, never a live rate limit. `packages/subagent/tool-subagent/tests/redaction.spec.ts` proves the redaction property directly: a credential-shaped label/value pair is redacted, a non-credential-shaped operational identifier (the measured `cf-ray`/`request id`) is not. `examples/acp-agent/tests/snapshots/subagent-classified-failure/` pins the exact model-visible text and the `tool/result` event's `error: {"name":"SubagentError","code":"SUBAGENT_AUTH"}` verbatim in a real assembled ACP session log.
