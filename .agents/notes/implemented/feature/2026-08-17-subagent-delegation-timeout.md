# Agent Note: A wall-clock timeout for delegated subagent runs

Status: implemented

English | [中文](2026-08-17-subagent-delegation-timeout.zh.md)

## Problem

Neither out-of-process subagent protocol has a timeout. `ThreadStartParams`/`TurnStartParams` (`subagent-codex`) and the SDK `Options` (`subagent-claude-code`) carry no field for a wall-clock bound, and the existing `disposeGraceMs` config on `subagent-codex` is teardown grace after a stop decision, not a bound on how long a run may take before that decision is made. Measured against a real unauthenticated Codex CLI: the app-server retries a WebSocket connection 5 times, then falls back to HTTPS for 5 more retries, before it finally fails — a wedged, expired-login delegation is indistinguishable from a hung one for as long as that retry ladder runs, and nothing in `dsh-tool-subagent` or either provider stops it sooner.

## Decision

`dsh-tool-subagent`'s `Config` adds `timeoutSeconds?: number`, a positive finite number no greater than `MAX_TIMER_DELAY_MS` (`@deepseek-ai/dsh-timeout`) in milliseconds, validated with the same `assertPositiveFinite` helper `subagent-codex`'s `disposeGraceMs` already uses (both at the Loader's schema path and at a direct `apply()` call that bypasses Schemastery, mirroring the existing `maxDepth` dual-path coverage). No Schemastery `.default(...)`: PR1 (the permission-scope note below) learned this the hard way for `permissionMode` — a materialized default here would silently cut off every existing `spawn`/`fork` composition's long-running delegations the moment this package upgrades. Omission preserves today's behavior exactly: no cap.

The timer is owned by `dsh-tool-subagent`, not by `dsh-subagent` or either out-of-process provider. The tool already holds `exec.signal` and builds `SubagentStartRequest.signal` from it; `packages/util/timeout`'s `deadline(exec.signal, timeoutMs, 'SUBAGENT_TIMEOUT')` fuses that upstream signal with an `AbortSignal.timeout`-equivalent armed timer into one composed signal, which is what actually reaches `ctx.subagents.start()`. `timeoutMs <= 0` (the omitted-`timeoutSeconds` case) is `deadline()`'s own no-timer sentinel: it forwards the upstream signal **by identity**, so an omitted cap allocates neither a timer nor a distinct signal object — a delegation-heavy composition that never sets this field pays nothing for the feature's existence. The timer starts before `ctx.subagents.start()` is called, not after it resolves, and covers that call inside a `try`/`catch`: the motivating Codex retry-loop failure wedges during startup, not during the awaited result, so a timeout that only wrapped `run.result` would miss the case this note exists for.

Because the tool holds the timer, it already knows whether an `aborted` result came from its own expiry or from the caller's own cancellation — `timeoutOf(deadlineSignal, 'SUBAGENT_TIMEOUT')` recovers the `TimeoutReason` exactly when this instance's timer won the race, distinguishing it from a genuine caller cancellation even when both race the same composed signal. `stopReasonError()` uses this to report `subagent run hit its <N>s time limit before finishing` (mirroring the existing `max-tokens` headline's shape, phrased from the model's perspective, no timer/signal/abort vocabulary) instead of the unconditional `subagent run was cancelled` it used before this change; every other `aborted` result, including a real caller cancellation racing an armed timer, still reads as cancelled. `withPartialText()` is unchanged and still appends any preserved partial output after either headline. `using` (TC39 explicit resource management) owns the foreground timer's disposal; the foreground branch necessarily `await`s the settlement promise instead of returning it bare, because a bare `return settleForegroundRun(...)` would let the `using` block's synchronous exit clear the timer before the returned promise ever settles — before the timeout could fire at all.

`timeoutSeconds` applies to a foreground call and a one-shot background call — both runs this tool owns start-to-finish. It is rejected at `apply()` (config-vs-config, fully self-contained, so it fails at load like the existing empty-`toolFilter` check) together with `backgroundMode: 'continuable'`: a continuable child's turns are owned by the continuation manager after inbox acceptance, not this tool, so there is no run here for a timer to stop. The one-shot background path composes the same `deadline()` around the job-owned `AbortController`'s signal and disposes it in the job's `done` promise's `.finally()` (a bare `using` cannot span a synchronous closure that returns before the async work completes); `SubagentResult`/`SubagentStopReasonMap` stay untouched, so the generic task surface (`job_output`, the settlement notice) still reports a timed-out one-shot child as `[status: killed]`, identical to an explicit `job_kill` — see Known Limitations.

`subagent-codex`'s `real-product.spec.ts` adds a test proving the SAME quiescent teardown the existing manual-cancellation test proves, but firing from `dsh-timeout`'s `deadline()` on a real elapsed timer instead of an explicit `controller.abort()` call — the provider needs no change because both paths converge on the identical signal-abort contract; this is deliberately in the provider's own suite, not a new dependency from `subagent-codex` on `dsh-tool-subagent`, because process-tree teardown under an aborted signal is a provider-owned guarantee independent of which caller's composition produced the abort.

## Alternatives considered

- **A `timeout` variant added to `SubagentStopReasonMap`** — rejected: the tool that starts the timer already knows why its own signal aborted (`timeoutOf()` on the composed signal it built), so widening a contract shared across every provider and every `dsh-subagent` consumer buys nothing here. The stop-reason union crosses a capability seam boundary (`docs/glossary.md#capability-seam`); this change is local to one tool instance's own composed signal and belongs there, not on the seam.
- **A failure-detail channel on `SubagentResult`** (e.g. a `timedOut: boolean` field) — rejected for the same reason and because the spec draws this boundary explicitly: general error classification (auth/quota), `changed_files`, `usage`, and session continuation are separate, later work: this change stays scoped to one wall-clock bound and its model-facing report.
- **A materialized default `timeoutSeconds`** (e.g. `z.number().default(120)`) — rejected: identical failure mode to the `permissionMode` default PR1 rejected. A default forwarded unconditionally would silently truncate every existing `spawn`/`fork` composition's long-running delegations on upgrade; only an explicit deployment opt-in is safe.
- **Wrapping only `run.result`, not `ctx.subagents.start()`** — rejected: the empirically measured failure (Codex's unauthenticated 10-attempt WebSocket/HTTPS retry ladder) happens during startup. A timer that only bounded the awaited result would leave exactly this case unbounded.
- **Distinguishing a timed-out one-shot background run in `JobOutcome`** — deferred, not rejected outright: `dsh-jobs`'s `JobOutcome`/`runOutcome()` (`packages/subagent/subagent/src/run-settlement.ts`) is a shared contract with every other job kind, and `aborted → { status: 'killed' }` already collapses a `job_kill` and a provider-side abort into one report today; widening it for this one caller is a larger, separately-scoped change. Recorded under Known Limitations in the package README instead of solved here.

## Consequences

- A `spawn`/`fork`/`acp`/`dsh-sdk` composition that never sets `timeoutSeconds` is completely unaffected: no timer, no distinct signal object, byte-identical tool schema (the field is deployment configuration, never a model-facing tool argument).
- A deployment that sets `timeoutSeconds` gets a hard wall-clock bound on both the child's startup and its full run, covering the measured Codex retry-loop failure and any future provider with a similarly slow failure path, without either provider needing its own timeout mechanism.
- The model can tell a timeout apart from every other terminal outcome (`cancelled`, `failed`, `token limit`, `declined`, an unrecognized future reason) by reading the foreground tool result alone; a one-shot background run's timeout is not yet distinguishable through the generic task surface (Known Limitations in the package README).
- `timeoutSeconds` and `backgroundMode: 'continuable'` are mutually exclusive on one tool instance; a deployment needing both bounds a continuable provider's own runtime instead (out of this change's scope).
- `packages/subagent/tool-subagent/tests/tool-subagent.spec.ts` covers: the timeout headline distinct from cancellation, a start-phase timeout with the same headline as a result-phase one, a caller cancellation racing a configured (longer) cap still reading as cancelled, the omitted-cap path forwarding the exact upstream signal (proving no timer or wrapper signal is allocated), the load-time rejection with `backgroundMode: 'continuable'` on both the schema and the direct-`apply()` path, and invalid `timeoutSeconds` values (zero, negative, `NaN`, both infinities, and a value beyond `MAX_TIMER_DELAY_MS`) on both paths. `packages/subagent/subagent-codex/tests/real-product.spec.ts` covers quiescent teardown under a real elapsed deadline against the real app-server process tree. `examples/acp-agent/tests/snapshots/subagent-timeout/` is a keyless assembled-app snapshot: a forked child's real `bash` call blocks on a real `sleep`, the configured 0.2-second cap fires mid-call, and the persisted parent log pins the exact model-visible headline text (`subagent run hit its 0.2s time limit before finishing`) verbatim. That fixture's determinism rests on the fork child consuming its one scripted model call and reaching the `bash` call within the 0.2-second cap (measured local margin: roughly 5x headroom); if a heavily loaded CI runner ever misses it (symptom: `assertConsumed` reporting an unbound child script), raise `timeoutSeconds` in both `subagent-timeout.cordis.yml` and `subagent-timeout.cordis.snapshot.yml` and re-run `pnpm run test:snapshot:refresh -t subagent-timeout`.
