# Agent Note: opt-in provider-native resume/continuation for delegated `codex`/`claude-code` runs

Status: implemented

English | [中文](2026-08-18-subagent-delegation-resume.zh.md)

## Problem

A one-shot `codex`/`claude-code` delegation always starts fresh: every call pays for the child's system instructions and tool schemas again, and a model that wants to continue a specific prior delegation (not start another one) has no way to do so — its only option is a new, context-blind run. Both native products already support exactly this through their own protocols (Codex's persistent `thread/resume`, the Claude Agent SDK's `Options.resume`), but PR1–PR4 (permission scope, timeout, failure classification, changed-files/usage) deliberately left continuation out of scope.

Four requirements shaped the design, three of them security-relevant:

1. **Pure opt-in.** Neither provider's default behavior may change: Codex stays `ephemeral: true` and Claude stays `persistSession: false` unless a call explicitly asks for persistence. A composition that never opts in must see a byte-identical tool schema, result schema, and logged `tool/result` shape to a pre-PR5 subagent call.
2. **A model-supplied resume id is untrusted input that must be scope-bound.** The child process inherits the harness's own `HOME`, so it shares the user's own private `~/.codex`/`~/.claude` conversation stores. Without a check, a model that learns or guesses an id from a differently-scoped delegation (a different tool row, a different `permissionMode`, a different cwd) could resume into a wider-scoped or unrelated conversation than the one it was ever granted.
3. **Authorization must be log-derived, never an in-process cache.** A harness Session survives process restarts; an in-process Map of "ids this process issued" would silently stop authorizing legitimate resumes across a restart while adding no real security (an attacker just waits for the next restart), so the authoritative check has to read the Session's own durable event log.
4. **The wire details are provider-specific and easy to get backwards.** Codex's app-server JSON-RPC field is camelCase `threadId`, not the Rust source's `thread_id`; the ephemeral/persistent assertion has to invert correctly on the opt-in path; and the actual per-call usage-accounting question (does resuming replay a whole-thread cumulative total?) is not documented anywhere and had to be measured.

## Decision

### Two-layer gate, not one

Unlike `permissionMode` (deployment-only, because widening a child's OS-level permission scope is never the delegating model's decision — see the [pinned-approval Note](2026-08-10-subagent-approval-pinned-never.md)), resume is a two-layer gate: `dsh-tool-subagent`'s deployment-level `allowResume: boolean` config (default `false`) decides whether the `resume`/`resume_id` tool arguments exist in the model-visible schema AT ALL; within that gate, the model's own per-call `resume: true` or `resume_id: "<id>"` is a legitimate request, not a scope-widening one — continuing a specific prior run is exactly the kind of decision the calling model is positioned to make, unlike granting itself a wider permission scope. `allowResume: true` requires the configured provider's new `resume` capability and fails the mount without it, and rejects combination with `backgroundMode: 'continuable'` at load — the two mechanisms solve different problems (a durable, harness-owned multi-turn child vs. a provider-native thread continued outside the harness's own turn model) and would otherwise both compete to own one tool row's continuation semantics.

`SubagentCapabilities` gains `resume: boolean`. `spawn`/`fork`/`acp`/`dsh-sdk` all declare `false` — an in-process provider shares the parent's own Cordis authority and has no separate native thread to persist. `codex` and `claude-code` declare `true`. `SubagentStartRequest` gains `requestResume?: boolean` (ask to keep this run's thread/session alive) and `resumeId?: string` (continue a specific prior one); `SubagentResult` gains `resumeId?: string` — ALWAYS the provider's own reported identity (Codex's `thread.id`, Claude's `session_id`), never an echo of the request's `resumeId`.

### Resume authorization is log-derived, scope-bound, and lives in the shared seam

`packages/subagent/subagent/src/resume-issuance.ts` is new. `SubagentResumeIssuance` is `{ id, provider, permissionMode, cwd }` — the id plus the EXACT scope it was issued under. `SUBAGENT_RESUME_META_KEY = 'subagentResume'` is the `tool/result.meta` object key a consumer logs this record under (exported so `dsh-tool-subagent`, the one shipped writer, and this verifier agree on the wire shape without either depending on the other's package). `verifyResumeIssuance(session, candidate)` scans `session.events` for a `tool/result` event whose `meta[SUBAGENT_RESUME_META_KEY]` matches `candidate` on ALL FOUR fields, not `id` alone.

`SubagentRuntime.start()` calls `assertResumeAuthorized()` whenever `request.resumeId !== undefined`, AFTER `assertCapabilities()` (an unsupported-capability rejection stays distinct from a scope rejection) and BEFORE any provider ever sees the id. It builds the candidate from `request.parent.session.header.cwd` (rejecting immediately, with no session scan at all, when the parent's header carries no cwd) and the REQUEST's effective `permissionMode` (`request.permissionMode ?? 'read-only'` — the provider's own documented default), never the raw deployment config value. Comparing effective-to-effective, not raw-config-to-raw-config, is what correctly treats two tool rows against the same provider — one omitting `permissionMode` (defaulting to `'read-only'`), the other spelling out `permissionMode: 'read-only'` explicitly — as the SAME scope, while still rejecting a genuinely different one. A rejected resume — whether the id was never issued at all, or was issued under a different provider/scope/cwd — always throws the SAME `SubagentError` (`RESUME_REJECTED`, "subagent resume id was not issued in this scope by this harness session"): a model that could distinguish "wrong id" from "wrong scope" would gain a probing oracle for nothing.

### Codex: `thread/resume`, camelCase, re-pinned sandbox, inverted assertion

`CodexAppServerWire.startThread()` gains a `persistent` parameter (default `false`): it sends `ephemeral: !persistent` and validates the returned `thread.ephemeral` against the REQUESTED value — inverted from the pre-PR5 assertion, which only ever checked for `ephemeral: true`. A new `resumeThread(threadId, permissionMode, signal)` sends `thread/resume { threadId, sandbox, approvalPolicy: 'never' }` — **measured: the field is camelCase `threadId`; the Rust source's snake_case `thread_id` is rejected by the app-server's own field-name validation with `-32600 "missing field threadId"`.** `sandbox`/`approvalPolicy` are re-pinned on every resume exactly as `thread/start` pins them on creation, so a resumed child's permission scope is always THIS call's `permissionMode`, never whatever scope the thread happened to run under previously (the harness-level scope check above is the primary defense; this is defense in depth at the wire itself). A `thread/resume` JSON-RPC error (unrecognized/already-in-use id) is caught and reclassified as a `ClassifiedSubagentFailure { code: 'provider', ... }` — the SAME classification a post-publication native failure gets — because this rejection happens BEFORE any thread is ever (re-)published, a code path PR1–PR4 never needed. A non-`JsonRpcResponseError` classified failure (a malformed `thread/resume` response shape) is rethrown unchanged. A resumed thread whose returned id does not match the requested one is rejected as a defensive integrity check.

### Claude: `Options.resume`, `persistSession`, no fork, existing classification already covers the failure paths

`claudeQueryOptions()` computes `persistent = spec.requestResume || spec.resumeId !== undefined` and sets `persistSession: persistent` (default stays `false`) plus `resume: spec.resumeId` when set. `forkSession` is deliberately unused: this mechanism continues the SAME `session_id` across calls; it does not branch a new session from an existing history, which is a different (and unneeded) SDK feature. `consumeClaudeQuery()` captures `message.session_id` into the reported `resumeId` only when `persistent` and the run succeeds. `settingSources: []` and the fixed `canUseTool` permission scope remain enforced on a resumed call exactly like a fresh one — resuming grants no additional trust.

**Measured: resuming from a mismatched cwd, or resuming an unrecognized session id, is not a thrown exception — it is a normal `is_error: true` result message carrying an actionable `errors` array** (e.g. `"No conversation found with session ID: 00000000-0000-0000-0000-000000000000"` for a fake id; the same message, naming the requested id, for a cwd mismatch — the SDK's on-disk session store is cwd-keyed). This is exactly why zero new Claude-side classification code was needed: this failure already flows through the EXISTING `is_error`/`api_error_status` classification path the failure-classification PR (PR3) built, landing as `SubagentFailureDetail { code: 'provider', ... }` with no dedicated resume-failure branch.

### The usage question: `total` is thread-lifetime cumulative, `last` is per-call — sum `last`, never read `total`

The spec flagged this as an open question: Codex's `thread/tokenUsage/updated` notification fires multiple times per turn; PR4 established that the notification's `total` field is a running total across an ordinary (non-resumed) turn, so the correct move there is to retain only the LAST observed `total`. Resume raises a new question PR4 never had to answer: does that `total` continue accumulating ACROSS a `thread/resume`, or does the app-server reset it for the "new" (resumed) thread instance?

Two standalone probe scripts against the real `codex app-server` binary settled it empirically. **`total` never resets across `thread/resume`.** A thread that accumulated `total: { inputTokens: 30, outputTokens: 11 }` from a prior two-response turn, once resumed, immediately received a `thread/tokenUsage/updated` replay notification still carrying that exact stale `total` — before the new turn's own first notification — and the new turn's own notifications continued incrementing FROM that stale base, not from zero. Retaining "the last observed `total`" (PR4's rule, unchanged) would therefore report a RESUMED call's usage as the entire thread's lifetime total, including every prior call's tokens — silently wrong the moment resume exists, even though it was correct for PR4's own non-resumable ephemeral threads.

The notification carries a second field, `last`, that PR4 never needed to read: the INDIVIDUAL model call's own usage, non-cumulative even within one turn. `observeTokenUsage()` now sums each notification's `last` field within the currently active turn only, and never reads `total` at all. This is the only construction that reports THIS call's own usage correctly on both a fresh thread (where it happens to telescope to the same value PR4's rule already produced) and a resumed one (where it does not). The rewritten unit test proves non-reliance on `total` directly: it feeds deliberately mismatched, inflated `total` values in the fixture notifications and asserts the summed result matches only the `last` fields. A real-product integration test exercises the full cross-process case: start a persistent thread, complete one turn, resume it, complete a second turn, and assert the SECOND result's reported `usage` equals only the second turn's own tokens.

Claude's `usage` field has no analogous trap: the Claude Agent SDK's terminal `result` message reports that call's OWN usage directly (there is no thread-lifetime-cumulative concept on the wire at all), confirmed by the real-product resume test asserting an exact usage value after a genuine cross-process resume.

### `presentationMeta` stays gated on `allowResume`, not unconditionally present

`dsh-tool-subagent`'s `output.presentationMeta` — the mechanism that writes the durable `tool/result.meta.subagentResume` issuance record — is present in the built `ToolDefinition` ONLY when `allowResume` is configured, using a conditional EXPRESSION (`allowResume ? fn : undefined as never`), not a conditional SPREAD into the `output` object literal. A conditional spread was tried first and rejected: it defeats `defineTool`'s `const O`/`execute()` generic inference (every downstream `execute` type collapsed to `never`). A plain ternary whose false branch is the bare `undefined` literal was tried next and rejected too, for a narrower reason: `exactOptionalPropertyTypes` rejects assigning `undefined` to an optional function property even inside a ternary, producing exactly one clean, local type error at that line — fixed with a single `undefined as never` cast on the false branch alone (`never` is assignable to anything), which does not touch the true branch's contextual inference at all. The net effect matters for the byte-identical guarantee: `defineTool` itself omits `output.presentationMeta` from the built tool entirely when the supplied value is `undefined` (see its own conditional spread), so `ctx.tools`'s `createSuccessResult()` never calls it and `tool/result.meta` stays FULLY ABSENT — not a `null` placeholder — for a composition that never sets `allowResume`, exactly matching a pre-PR5 subagent call.

### Pre-publication classified failures need a new tool-level entry point

Every prior classified-failure path (PR3) is post-publication: a `SubagentRun` is already published, and its `result` promise later rejects or resolves with `SubagentResult.failure`, settled through `settleRunResult()`. Resuming an invalid/unknown id is different: `thread/resume` can reject BEFORE any thread is ever published, so `ctx.subagents.start()` itself throws a `ClassifiedSubagentFailure` synchronously (well, as a rejected promise) with nothing yet published to settle. `dsh-tool-subagent` adds `rethrowStartupFailure(error)`: it converts a caught `ClassifiedSubagentFailure` to the SAME routable, redacted, class-specific `SubagentError` headline (`classifiedFailureHeadline()`) a post-publication failure already produces, reusing the existing presentation logic rather than duplicating it. A plain `SubagentError` (for example this seam's own resume-authorization rejection) passes through this function unchanged — it is already a routable `HarnessError`, not a native provider failure needing reclassification.

## Alternatives considered

- **An in-process `Map<resumeId, scope>` issued at start time, consulted at resume time** — rejected: a harness Session survives process restarts (this repo persists sessions to disk), so an in-process registry would silently stop authorizing a legitimate resume across a restart while adding no attacker-facing security a persistent, log-derived check does not already provide. The chosen design derives authorization from the same durable event log every other model-visible fact already lives in, so a resume works identically whether the authorizing call happened one second ago or across a process restart.
- **Comparing the RAW deployment `Config.permissionMode` value instead of the request's effective (already-defaulted) value** — rejected: it would treat one tool row that omits `permissionMode` (defaulting to `'read-only'`) and a second row that spells out `permissionMode: 'read-only'` explicitly as different scopes, purely because of how the deployment happened to phrase an identical effective grant, producing spurious `RESUME_REJECTED` failures for a model that has no way to know the difference. Comparing effective values closes exactly the real security gap (a genuinely wider scope) without this false-positive cost.
- **Two distinguishable rejection messages for "id never issued" vs. "id issued under a different scope"** — rejected: it would hand a model a probing oracle (repeatedly guessing ids and reading back which failure it got would let it map out valid ids/scopes it does not hold). One indistinguishable `RESUME_REJECTED` message closes this for free.
- **`forkSession` for the Claude side** — considered and rejected: `forkSession` branches a NEW session from an existing history, while this feature's actual requirement is continuing the SAME `session_id` across calls (a model resuming its own prior delegation, not branching an alternate timeline of it). Using it would have been a different, unneeded feature.
- **Distinguishing the Claude resume failure paths (bad id vs. cwd mismatch) with dedicated classification code** — rejected once measured: both surface as the identical SDK-level `is_error: true` result-message shape the EXISTING failure-classification path (PR3) already handles; adding dedicated code would duplicate working classification for a distinction the SDK itself does not make on the wire.
- **A conditional spread of `presentationMeta` into `output`** — tried first, rejected: collapses `defineTool`'s generic inference for the entire call (see "presentationMeta stays gated" above).
- **A plain ternary (`allowResume ? fn : undefined`) with no cast** — tried second, rejected: `exactOptionalPropertyTypes` rejects the bare `undefined` false branch; fixed with a targeted `as never` cast on that one branch instead.
- **Retaining PR4's "last observed `total`" rule unchanged for a resumed thread** — tried first (before the probe), rejected once measured: `total` never resets across `thread/resume`, so it would report a resumed call's usage as the thread's entire lifetime total rather than that call's own tokens.
- **`prepareContinuable`** — explicitly out of scope for this PR (per the work order): it is the mechanism for a durable, harness-owned, session-backed continuable child (PR unrelated to this one), not a provider-native out-of-process thread/session continuation. The two remain mutually exclusive on one tool row (see "Two-layer gate" above).

## Consequences

- A composition that never sets `allowResume` (the default) is completely unaffected: identical tool schema, identical result schema, identical rendered text, and identical `tool/result` event shape (`meta` fully absent, not `null`) to a pre-PR5 subagent call. `spawn`/`fork`/`acp`/`dsh-sdk` declare `resume: false` and are never asked to support it.
- An `allowResume: true` deployment on `codex`/`claude-code` lets a model continue a specific prior delegation's exact context across calls, at the cost of provider-native process/thread/session state living longer than one tool call.
- **A resumed thread/session becomes visible in the host's own product history.** Codex's persistent thread is stored in `~/.codex`'s conversation history exactly like the user's own interactive sessions; Claude's resumed session is stored in `~/.claude/projects/`, cwd-keyed, and appears in the user's own `claude --resume` picker. This is a durable, host-visible side effect a deployment opting into `allowResume` should expect, not an internal implementation detail.
- **The Claude store is cwd-keyed**, so resuming from a cwd different from the one the session was created in fails (classified `provider`, via the existing `is_error` path) — a real, measured constraint, not a bug: the resumed child's workspace is fixed at the ORIGINAL delegation, and this provider never tries to relocate a persisted session to a new cwd.
- **Replaying the parent Session log no longer reproduces a resumed child's internal state.** The model-visible ⟺ logged invariant still holds fully for the PARENT's own log (the resume id, the request, the result are all faithfully reconstructable), but the CHILD's own provider-native thread/session evolves independently across resumes — replaying the parent's log a second time does not re-derive what the child's persisted state now contains, unlike a purely in-harness, non-resumable child whose entire behavior is a deterministic function of its logged request.
- A resume attempt this session never authorized fails BEFORE reaching the provider, with zero provider-side calls made (proven directly: the security regression tests assert the scripted/real provider's own call counter stays at zero).
- Codex's `usage` field on ANY completed run (resumed or not) now sums `last` per turn instead of retaining the last observed `total` — a correction that happens to be invisible for a non-resumed thread (both constructions telescope to the same value there) but was necessary once resume exists, since `total` is thread-lifetime cumulative.

Every OTHER existing keyless snapshot (including every other subagent scenario) is untouched and passes unchanged, because no shipped composition sets `allowResume` — this is the byte-identical-default guarantee holding at the snapshot layer, not just the unit-test layer.
